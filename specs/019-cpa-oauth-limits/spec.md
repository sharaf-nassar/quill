# Spec: cpa-oauth-limits

## Problem Statement

Quill's LIMITS band shows one row per natively-integrated provider (Claude, Codex, MiniMax), each backed by a single credential that Quill reads directly (Anthropic OAuth usage API, Codex app-server, MiniMax API key). A growing class of power users no longer holds one account per provider: they run a local **CLI Proxy API** (CPA — the open-source Go project `router-for-me/CLIProxyAPI`) that pools *multiple* OAuth accounts per provider (Claude Code, Codex/ChatGPT, Gemini CLI, Antigravity, Grok Build, Kimi, Qwen, iFlow, …) behind OpenAI/Claude/Gemini-compatible endpoints, with round-robin or fill-first routing and per-credential quota/cooldown state.

For these users Quill's current LIMITS band is wrong twice over: it shows at most one account's limits per provider (whichever credential Quill happens to read directly), and it says nothing about the pool the user actually burns through. The user's real question — "how much headroom do I have across all my accounts, and which account is about to hit a wall?" — is unanswerable in Quill today. Ecosystem tools (Quotio, QuotaBar, CLIProxyAPI-Quota-Inspector) exist precisely to fill this gap, which confirms demand; Quill should answer it in its own widget rather than sending users to a second monitoring app.

Why now: CPA has become the de-facto local multi-account manager for AI coding subscriptions, it exposes a documented localhost Management API that carries exactly the account inventory and health state Quill needs, and Quill's LIMITS band was just redesigned (spec 018) so per-account extension is cheapest to do while that surface is fresh.

## Goals

1. **CPA as a first-class credential/usage source.** Quill can be pointed at a locally running CPA instance (endpoint + management key) and treats it as a usage source alongside the existing direct integrations, following the existing service-only provider pattern (like MiniMax: no CLI/home detection, configured via stored secret).
2. **Per-account visibility.** For every OAuth credential CPA manages, Quill can show: provider, account identity (email/label), health (`ready` / `disabled` / `unavailable` / cooldown), and — for Claude and Codex accounts, in scope for v1 — the same rate-limit windows the native rows show (e.g. Claude 5h/weekly utilization %, Codex 5h/weekly), fetched per account via CPA's verified `api-call` mechanism, with the standard 50/80 severity ramp and reset countdowns. Health-only display is the per-account degradation when a window fetch fails (Clarifications Q2).
3. **Useful aggregate.** The LIMITS band shows, per CPA-backed provider, a worst-case aggregate row that answers "how much pool headroom is left" at a glance: per window, aggregate utilization = max utilization across healthy accounts, plus a count of healthy vs. total accounts (e.g. `3/4`) (Clarifications Q1).
4. **Fits the 360px widget.** All of the above fits the Flat Polish design at the widget's 360px design width without turning LIMITS into a scrolling table — aggregate-first, detail on demand: tap/click expands indented per-account sub-rows under the aggregate row, capped at ~6 before "…and N more" (Clarifications Q5).
5. **Degrades exactly like existing providers.** CPA down/unreachable produces the same degraded ladder as native providers: cached snapshot fallback, network backoff via `compute_network_backoff`, `stale`/`offline`/`paused` provider errors, titlebar sync-pill states. No new error vocabulary.
6. **Measurable acceptance:** with a CPA instance holding N ≥ 2 Claude accounts and M ≥ 2 Codex accounts, the LIMITS band shows CPA-backed rows covering all N+M accounts (aggregated or listed), an unavailable account is visibly distinguished within one poll cycle (≤ 3 min), and killing CPA flips the rows to the cached/offline treatment within one poll + backoff cycle.

## Non-Goals

- **Managing CPA.** Quill will not add/delete/disable CPA auth files, trigger OAuth login flows, edit CPA config, rotate API keys, change routing strategy, or call `POST /reset-quota`. Read-only in v1 (a "reset quota" affordance is a tempting follow-up; explicitly out of scope here).
- **Proxying Quill's own inference through CPA.** Quill's insights/inference pipeline keeps its existing paths; CPA is a usage/credential *source*, not a model gateway for Quill.
- **Installing, launching, or supervising the CPA process.** Quill assumes the user runs CPA themselves; no bundled binary, no lifecycle management (unlike some ecosystem tools).
- **Request-level analytics from CPA.** `GET /usage-queue` is a *destructive* pop of per-request records intended for telemetry consumers; Quill will not consume it in v1 (it would race the user's other consumers). Token/request analytics stay driven by Quill's own session indexing.
- **Cost estimation** for CPA-routed traffic.
- **Remote CPA instances.** v1 targets localhost only (`http://127.0.0.1:<port>`); remote `allow-remote` deployments are out of scope (and would violate the no-new-off-device-transmission constraint).
- **Redesigning the Manage window** beyond the minimum settings surface needed to configure the CPA endpoint/key (Manage keeps its current density per DESIGN.md §6 migration exception).
- **Dedup of the same account across direct and CPA sources (v1).** Both rows are shown; potential double-count of the same underlying account is accepted and documented (Clarifications Q3).
- **Per-provider rows for non-native CPA providers.** Gemini, Qwen, Kimi, xAI, Antigravity, iFlow, etc. surface only as a single neutral count line (e.g. `+3 other accounts`) — no rows, no new provider identities or swatch colors (Clarifications Q4).
- **Zero-config discovery of endpoint/key.** Manual entry only; the management key is unrecoverable from disk anyway (`config.yaml` stores only a bcrypt hash of it).
- **OS-keyring storage of the management key.** v1 uses a plain SQLite settings row; keyring migration is a separate follow-up issue filed at create-beads (Clarifications Q6).
- **Routing-strategy-aware or capacity-weighted aggregates.** v1 aggregate is worst-case only (Clarifications Q1).
- **Account enable/disable toggle** (`PATCH /auth-files/status`) and any **reset-quota affordance** — restating the read-only rule above as explicit, pre-declared day-after asks.
- **Multi-instance support.** v1 is single-instance; the settings shape must not preclude a list of instances later.

## User Stories

### US-1: Connect Quill to CPA

As a **CPA user**, I want to point Quill at my local CLI Proxy API instance (URL + management key), so that Quill can read my pooled OAuth accounts without me re-authenticating each one inside Quill.

**Acceptance Criteria:**
- A settings surface accepts a CPA base URL (default `http://127.0.0.1:8317`) and a management key; the key is stored in Quill's local SQLite settings (same storage class as the MiniMax API key) and never leaves the device except in requests to the configured localhost endpoint.
- On save, Quill validates the connection by calling `GET /v0/management/auth-files` with `Authorization: Bearer <key>` and reports success or a typed failure (unreachable vs. 401/bad key vs. unexpected response) with distinct user-facing messages.
- Disabling/removing the CPA integration deletes the stored key and removes all CPA-sourced rows from the LIMITS band on the next emit, mirroring `confirm_disable` behavior for existing providers.

### US-2: See every pooled account's health

As a **user with multiple OAuth accounts per provider in CPA**, I want the LIMITS band to reflect every account CPA manages — including which ones are disabled, unavailable, or cooling down — so that I know my real pool state, not just one account's.

**Acceptance Criteria:**
- Quill polls `GET /v0/management/auth-files` on the existing 3-minute usage cadence and maps each entry's `provider`, `email`/`label`/`account`, `status`, `status_message`, `disabled`, and `unavailable` fields into per-account state.
- An account with `unavailable: true` or `disabled: true` is visually distinguished (not counted as healthy headroom) within one poll cycle.
- Accounts for a given provider are grouped under that provider's identity (swatch + name) — never N unrelated top-level rows per account at 360px; the presentation is one aggregate row with expandable indented per-account sub-rows (Clarifications Q5).
- The healthy/total count (e.g. `3/4`) shown for a provider always equals the number of entries with `status == "ready"` and neither `disabled` nor `unavailable` set, over the total entries (`runtime_only` entries included by default; final inclusion rule is an implementation detail — OQ13).

### US-3: See per-account rate-limit windows

As a **user rationing subscription quota**, I want each CPA-managed account to show the same rate-limit windows Quill already shows for native providers (utilization %, window label, severity bar, reset countdown), so that I can tell *which* account is nearly exhausted rather than just that one is.

**Acceptance Criteria:**
- For providers where Quill already knows the upstream quota API (Claude: Anthropic OAuth usage API; Codex: ChatGPT `wham/usage`), Quill obtains per-account windows for each CPA credential via the VERIFIED standardized mechanism — CPA's `POST /v0/management/api-call` with `authIndex` and `$TOKEN$` header substitution (see the verified research log) — and renders them as `UsageBucket`-shaped cells with the existing 50/80 severity ramp and stale handling. A settings-flow smoke test (one `api-call` per provider on connect) validates the path end-to-end before window polling is enabled.
- If per-account windows cannot be fetched for an account (mechanism unavailable, token refresh failure), the account still appears with its health state and a clearly non-numeric placeholder — never a fabricated 0% or stale % presented as live.
- Reset countdowns use the existing `resets_at` semantics: a bucket past its reset renders neutral/stale, never as live severity.

### US-4: Aggregate pool headroom at a glance

As a **user glancing at the widget**, I want one aggregate readout per CPA-backed provider that summarizes pool headroom, so that I don't have to mentally combine four accounts' bars while a job is running.

**Acceptance Criteria:**
- Each CPA-backed provider gets exactly one always-visible aggregate row in LIMITS at 360px, showing at minimum: provider identity, an aggregate utilization signal per window, healthy/total account count, and the nearest relevant reset countdown.
- The aggregate is worst-case: per provider and window, aggregate utilization = max utilization across healthy accounts (healthy = `status == "ready"`, not disabled/unavailable/cooling), so its severity color is never *less* alarming than the pool's true state. Disabled/unavailable/cooling accounts are excluded from the aggregate math but count in the denominator of the healthy/total display. Accounts with missing/failed bucket fetches are excluded from the max and surfaced as a gap — never invented data; if ALL healthy accounts are missing buckets, the aggregate shows a non-numeric placeholder (Clarifications Q1).
- Aggregate math is a documented pure function with unit-testable semantics (inputs: per-account buckets + health flags; output: aggregate buckets + count), traceable to a lat.md section.

### US-5: CPA outage degrades gracefully

As a **user whose CPA instance is stopped or restarting**, I want Quill to show the last known pool state with the standard degraded treatment, so that a proxy blip doesn't dump alarming zeros or empty rows into the widget.

**Acceptance Criteria:**
- CPA connection failures feed the existing per-provider cooldown machinery (`compute_network_backoff`: 60s base half-jitter exponential, 30-min cap) and do not block or delay the other providers' polls (all provider fetches remain independent/off the UI thread).
- While CPA is unreachable, LIMITS shows the cached snapshot with the existing stale/offline provider-error treatment and the titlebar sync pill reflects the degraded state using the existing cached/paused/offline vocabulary.
- Recovery is automatic: once CPA responds again, the next successful poll clears the error state without user action.

## Constraints

**Quill current-state (verified in this worktree):**
- LIMITS band (`src/components/widget/LimitsSection.tsx`): one row per *enabled* provider — identity swatch, provider name, fixed-width cell per rate-limit window (rounded %, short window label, 4px severity bar), right-aligned nearest-reset countdown; severity thresholds 50% amber / 80% red; buckets whose `resets_at` elapsed render `stale` (neutral); 10s countdown tick; row states `ready | pending | setup | unavailable`.
- Usage plumbing (`src-tauri/src/lib.rs`, `src-tauri/src/models.rs`): `UsageBucket { provider, key, label, utilization, resets_at, sort_order }`, `UsageData { buckets, provider_errors, provider_credits, error }`; backend polls every 3 min; per-provider network cooldown via `compute_network_backoff` (60s base, half-jitter exponential, 30-min cap); cached snapshots persisted (`get_latest_usage_buckets`) with stale/offline/paused `UsageProviderError` kinds surfaced on the titlebar sync pill.
- Integration pattern (`src-tauri/src/integrations/`): `IntegrationProvider` enum currently `{Claude, Codex, MiniMax}`; MiniMax is the **service-only** template (`minimax.rs`: always "installed", no CLI/home detection, API key in SQLite settings, enable = save key, disable = delete key). CPA should follow this pattern. Provider statuses persist as JSON and emit `integrations-updated`.
- The LIMITS band assumes `UsageBucket.provider` is an `IntegrationProvider` — introducing per-account rows and possibly non-native providers (Gemini, etc.) will pressure this type; any extension must keep TS/Rust serde types in lockstep. Resolved: keep the enum; add optional `#[serde(default)]` account fields to `UsageBucket` plus new NULLABLE SQLite columns via migration (Clarifications Q7). The TS mirror (`src/types.ts`) is hand-maintained and updates in lockstep.

**Constitution constraints (apply in full):**
- **Local-first; opt-in external transmission.** CPA is a localhost service, so no *new off-device* transmission is introduced — the management key is stored as a plain SQLite settings row (MiniMax parity, per Clarifications Q6), never logged, never in telemetry. Requests are restricted to the configured loopback endpoint in v1: the base URL is validated loopback-only, rejecting any host other than `127.0.0.1`/`localhost`.
- **Rust/Tauri + strict-TS boundary.** All CPA HTTP calls live in the Rust backend; the frontend receives typed snapshots only. No fetches from the webview.
- **Work off UI threads.** CPA polling joins the existing async usage refresh; per-account fan-out (N accounts × window fetches) must be bounded/concurrent-limited so a large pool doesn't stretch the poll cycle.
- **Transactional, recoverable mutation.** Settings writes (endpoint/key) go through existing storage mutation guards; enable/disable follows the `confirm_enable_with_key`/`confirm_disable` shape.
- **Typed failures.** New failure modes (unreachable, 401 management key, malformed response, `api-call` upstream failure per account) get typed error kinds, not stringly-typed catch-alls; per-account failures must not fail the whole provider snapshot.
- **Zero-warning gates.** Rust and TS build clean; no `#[allow(dead_code)]` accretion beyond the existing pattern.
- **lat.md traceability.** New behavior (CPA source, aggregation function, degraded ladder) gets lat.md sections; key tests reference specs via `@lat:` comments.
- **DESIGN.md "Flat Polish".** No cards/gradients/glow; hairline-ruled bands; severity meter reserved for the green/amber/red ramp; fixed provider colors (Claude orange, Codex blue, MiniMax violet); density set at 360px design width with fluid bands. Per-account detail must not introduce a new visual language.

### Confirmed CPA facts (research log)

All confirmed against https://help.router-for.me/management/api and https://help.router-for.me/configuration/basic (CLIProxyAPI official docs, VitePress site for `router-for-me/CLIProxyAPI`), and the repo README (https://github.com/router-for-me/CLIProxyAPI), retrieved 2026-08-01:

- Management API base path: `http://localhost:8317/v0/management`; changes persist to the YAML config and hot-reload.
- Auth: every request (including localhost) needs a management key via `Authorization: Bearer <plaintext-key>` or `X-Management-Key`; `remote-management.secret-key` is bcrypt-hashed in `config.yaml`; remote access requires `remote-management.allow-remote: true`; `MANAGEMENT_PASSWORD` env and `cliproxy run --password` provide additional in-memory secrets.
- Config: `config.yaml`; `auth-dir` default `~/.cli-proxy-api`; inbound client `api-keys` list; `panel-github-repository` points at the `Cli-Proxy-API-Management-Center` web panel.
- `GET /auth-files` returns per-credential: `id`, `auth_index` (stable runtime id), `name`, `provider`, `label`, `status` (e.g. `ready`) + `status_message`, `disabled`, `unavailable`, `runtime_only`, `source`/`path`/`size`/`modtime`, cumulative `success`/`failed`, `recent_requests` (20 × 10-min buckets), `email`, `account_type`, `account`, `created_at`/`updated_at`/`last_refresh`. Health fields "mirror the runtime auth manager".
- `PATCH /auth-files/status` toggles `disabled`; `GET /auth-files/models` lists a credential's models.
- `POST /reset-quota {auth_index}` clears a credential's runtime quota/cooldown state and resumes it in routing — i.e. quota exhaustion is tracked as per-credential cooldown state inside CPA.
- `GET|PUT|PATCH /routing/strategy`: `round-robin` or `fill-first` credential selection. README confirms multi-account round-robin load balancing for Gemini, OpenAI/Codex, Claude, and Grok.
- `GET /usage-queue?count=N` pops per-request usage records (timestamp, latency, `auth_index`, token breakdown, provider, model, endpoint, auth_type); records are **removed** on read; legacy aggregate `/usage*` endpoints are gone. `GET /api-key-usage` gives recent request buckets grouped by provider/API key.
- OAuth account onboarding endpoints exist per provider (`/anthropic-auth-url`, `/codex-auth-url`, `/antigravity-auth-url`, `/kimi-auth-url`, `/xai-auth-url`, `/get-auth-status`, `/oauth-callback`) — out of scope for v1 but confirms CPA fully owns the OAuth lifecycle.
- `POST /api-call` performs an authenticated upstream HTTP request using a chosen credential (`auth_index`), substituting `$TOKEN$` in headers with that credential's access token; docs warn to restrict management-key access because of it.
- Quota-exceeded knobs `GET|PUT /quota-exceeded/switch-project` and `/quota-exceeded/switch-preview-model` exist (Gemini-oriented auto-switch behavior).
- Remaining UNVERIFIED items: port config key (moot — manual entry decided, OQ1) and upstream tolerance of per-account polling cadence (plan-time budget, OQ12). The `api-call` mechanism and the Codex HTTPS quota endpoint are now VERIFIED — see the follow-up findings below.

### Verified findings (follow-up research)

Retrieved 2026-08-01. Sources: CLIProxyAPI server source (`internal/api/server_management.go`, `internal/api/handlers/management/api_tools.go`), Cli-Proxy-API-Management-Center panel source (`src/services/api/apiCall.ts`, `src/features/quota/providers/*`), AllenReder/CLIProxyAPI-Quota-Inspector, and a live probe of the user's local instance (CPA v7.2.113 on port 8317).

- **STANDARDIZED QUOTA MECHANISM (verified 3 ways):** `POST /v0/management/api-call`, body `{authIndex, method, url, header{...}, data}`, response `{status_code, header, body}` (body = raw upstream string). `$TOKEN$` in any header value is replaced server-side with the credential's access token (refreshed if expired). 60s fixed timeout. No per-provider quota endpoints exist on the server.
- **NO SIDE EFFECTS:** the api-call handler builds its own `http.Client`; it does NOT touch success/failed counters, cooldown/quota state, or routing (sole exception: Antigravity token refresh persists rotated tokens — benign).
- **Claude quota via api-call:** `GET https://api.anthropic.com/api/oauth/usage`, headers `Authorization: Bearer $TOKEN$`, `anthropic-beta: oauth-2025-04-20`, `Content-Type: application/json`. ## Spec Review

Six parallel review passes (requirements, gaps, ambiguity, feasibility, scope, stakeholders) were run against this draft and the constitution. Overlapping findings are merged below; dimension tags show who flagged each. Constitution principles cited by number.

### Critical Questions (answer before planning)

1. **Aggregate semantics must be fixed to one function.** OQ8 lists four incompatible options; the sole stated invariant ("never less alarming than the pool's true state") is circular and only computable under worst-case/min-headroom semantics. "% remaining" is incomparable across plan tiers (Plus vs Max behind the same %), so capacity-weighted sums are not feasible from available data. Must also define: how `disabled`/`unavailable`/cooling accounts enter the denominator, and how accounts with *missing* buckets (fetch failed) enter the math without inventing data (P1, P10). Recommended v1: worst-case (max utilization across healthy accounts) per window + healthy/total count; defer routing-strategy-aware variants. — flagged by: requirements, ambiguity, feasibility, scope, gaps
2. **Per-account windows: verify the mechanism or scope it out of v1 acceptance.** US-3/US-4 hang on the UNVERIFIED `POST /api-call` + `$TOKEN$` pattern (OQ3); Codex likely has *no* route at all since Quill reads it via local `codex app-server` JSON-RPC, not HTTPS (OQ4). The spec must state whether the health-only fallback *satisfies* v1, and a live-CPA prototype must gate the plan if windows are in scope. This decision also owns the fan-out budget: N accounts × K windows every 3 min is Quill-*induced* off-device traffic to upstream quota APIs (P11), risks upstream rate limits/ToS exposure, and may pollute CPA's own success/failed counters and cooldown state — "read-only" is false in effect (needs verification). Explicit cadence/stagger/concurrency budgets required (P3, P10). — flagged by: requirements, feasibility, scope, stakeholders, ambiguity
3. **Coexistence and dedup rule for native vs CPA-sourced rows.** For a user whose `~/.claude` credential is also a CPA auth file: does the native row remain alongside the CPA aggregate, merge, or get replaced — and is the same account double-counted and double-polled? Undecided, this breaks the "one row per enabled provider" invariant and silently inflates headroom (P1). A concrete rule (e.g. "both shown, labeled, no dedup in v1" or "dedup by email where known") must be picked; note Quill's direct path may not know its own account email (unconfirmed). — flagged by: requirements, ambiguity, scope, stakeholders, feasibility
4. **v1 provider set: native-only or all CPA-held providers?** Goal 2 says "every credential CPA manages" but Gemini/Qwen/Kimi/Grok/etc. force new provider identities and swatch colors, colliding with DESIGN.md's fixed four-hue palette (P9) and expanding Quill's support surface. Recommended v1: Claude + Codex accounts only; non-native providers surface at most as a count ("+3 other accounts") or not at all — but this must be explicit either way, since "why doesn't my Gemini show up" is the guaranteed day-one ask. — flagged by: requirements, ambiguity, scope, stakeholders
5. **360px presentation: pin the MVP detail mechanism.** Goal 6 accepts "aggregated or listed" while US-4 mandates exactly one aggregate row and US-2 requires an unavailable account be "visibly distinguished" — if v1 is aggregate-row-plus-count only, an unavailable account is just a count decrement, which arguably fails US-2. Decide: aggregate row + expandable per-account sub-rows, hover/tooltip, or Manage-window drill-down; and the cap before "…and N more". Note `LimitsSection.tsx` is flat provider-keyed rows with no group/expansion concept — sub-rows are a component redesign, not an extension. Keyboard/screen-reader access to the chosen mechanism is constitutionally required (P9). — flagged by: requirements, ambiguity, scope, feasibility, gaps
6. **Management key storage posture.** The key authorizes `api-call` (arbitrary upstream requests with every pooled OAuth token), credential disable, and config edits — a categorically larger blast radius than the MiniMax key it's modeled on. Decide now: MiniMax-parity plain SQLite for v1 (explicitly accepted risk, keyring as separate follow-up) or OS-keyring/at-rest encryption as a prerequisite (new infrastructure Quill lacks) (P4, P11). — flagged by: stakeholders, feasibility, requirements, scope
7. **Snapshot schema and migration strategy for the account dimension.** `UsageBucket.provider` is the closed `IntegrationProvider` enum mirrored in TS and ~20 struct fields, with cached snapshots persisted in SQLite. Per-account rows and aggregates force a schema decision (account field vs new variants vs string provider) plus a stated old→new (and downgrade) migration story for persisted caches and provider-status JSON (P2, P4). Deciding after coding starts is the second-biggest rework risk. — flagged by: feasibility, gaps, requirements

### Non-Blocking Observations

- **Empty states:** define LIMITS behavior when CPA responds with zero auth-files, or zero accounts for a shown provider (hide vs SETUP); and startup-with-no-cache when CPA is down (SETUP vs UNAVAILABLE — OQ10).
- **Healthy/total formula:** fold the cooldown state into the numerator rule and resolve `runtime_only` inclusion (OQ13); current US-2 wording yields 3/4 vs 3/5 readings.
- **Version compatibility:** set a minimum CPA version or feature-detect; add a typed "unsupported version" failure distinct from unreachable/bad-key so old builds don't present as mystery outages (OQ16, P5).
- **Secrets/PII hygiene:** cached snapshots retain account emails/labels after disable — specify cleanup; exclude emails/`status_message` from logs and display-safe error strings (P5, P11).
- **Loopback enforcement:** specify the URL validation rule (reject non-`127.0.0.1`/`localhost` hosts) backing the v1 localhost-only constraint.
- **Null-impact guarantee:** state explicitly that an unconfigured CPA integration costs nothing — no probe traffic, no poll-cycle time, no UI changes (P3).
- **Diagnostics:** specify where per-account failure detail lives (tooltip/Manage/log) so a non-numeric placeholder is explainable without logging secrets (P5).
- **Minor ambiguities:** define "nearest relevant reset" for the aggregate row; bound the offline-flip acceptance window (backoff makes "one poll + backoff cycle" range 4–33 min).
- **Pre-declare day-after asks as out of scope:** account enable/disable toggle (`PATCH /auth-files/status`), `reset-quota` affordance, faster health-only polling, zero-config discovery (probe/parse config.yaml), multi-instance support (but shape settings storage to permit a list later), keyring migration.

- **Q1 — Aggregate semantics → DECIDED: worst-case.** Per provider and window: aggregate utilization = max utilization across healthy accounts (healthy = status `ready`, not disabled/unavailable/cooling); plus a healthy/total count (e.g. `3/4`). Disabled/unavailable/cooling accounts are excluded from the aggregate math but count in the denominator of the healthy/total display.
